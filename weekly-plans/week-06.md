## День 1 — Redis и кэширование

  инвалидация, stampede, `singleflight`.
- **Практика (90 мин):**

  - Кэш `GET /tasks/{id}`: сначала Redis, при промахе — Postgres, запись с TTL.
  - `singleflight.Group` вокруг загрузки из БД: 100 параллельных промахов → 1 запрос.
  - Инвалидация кэша при обновлении задачи.
  - Pipeline для 100 записей, сравни с 100 отдельными.
- **Закрепление (30 мин):** [go-redis docs](https://github.com/redis/go-redis),
  `go doc golang.org/x/sync/singleflight`.
- **Проект (30 мин):** кэш поверх P2, метрики hit/miss (пока просто счётчики).
- **Заметки:** какие данные нельзя кэшировать и почему.

## День 2 — asynq: задачи и воркеры

- **Теория (40 мин):** `asynq`: `Client.Enqueue`, `Server`, `ServeMux`, обработчик
  `func(ctx, *asynq.Task) error`, очереди и приоритеты, `MaxRetry`, `RetryDelayFunc`,
  `Scheduler` для периодических задач, архивирование (dead-letter).
- **Практика (90 мин):**
  - `cmd/worker` и `cmd/api` — два бинарника.
  - Тип задачи `report:generate` с JSON-payload.
  - Обработчик: обновляет статус в БД, шлёт прогресс, спит 2–5 секунд.
  - `asynq.NewServer` с `Concurrency: 5`, graceful shutdown `server.Shutdown()`.
  - Ретраи: 5 попыток, backoff с jitter; задача, которая всегда падает → в архив.
- **Закрепление (30 мин):** [asynq](https://github.com/hibiken/asynq) и
  [asynq wiki](https://github.com/hibiken/asynq/wiki).
- **Проект (30 мин):** схема `jobs(id, type, status, progress, error, created_at, updated_at)`.
- **Заметки:** чем очередь в Redis отличается от `go func()` и когда что выбирать.

## День 3 — Надёжность очередей

- **Теория (40 мин):** at-least-once vs exactly-once, идемпотентность по ключу,
  `idempotency_keys` таблица, transactional outbox, порядок операций
  «БД → очередь» и почему наоборот нельзя, двойная запись.
- **Практика (90 мин):**
  - Идемпотентность: `Idempotency-Key` в `POST /jobs`, повтор возвращает тот же `job_id`.
  - Outbox-вариант: запись задачи и события в одной транзакции, отдельный публикатор.
  - Обработчик проверяет «уже сделано?» перед побочным эффектом.
  - Тест: два одинаковых запроса → одна задача.
- **Закрепление (30 мин):** перечитай asynq wiki про retries и uniqueness;
  почитай про outbox pattern (любой внятный обзор).
- **Проект (30 мин):** реализуй идемпотентность в P3 + тесты.
- **Заметки:** где именно возникает дубль и как ты его ловишь.

## День 4 — WebSocket

- **Теория (40 мин):** HTTP upgrade, `coder/websocket` (`websocket.Accept`,
  `conn.Read/Write`, `conn.Ping`), origin check, ping/pong, read/write pumps,
  hub с подписками, backpressure (медленный клиент), auth при подключении.
- **Практика (90 мин):**
  - `GET /jobs/{id}/events` → upgrade, проверка токена до `Accept`.
  - Hub: map[userID]set[*conn], `sync.RWMutex`, broadcast, удаление при отключении.
  - Отдельная горутина на клиента: читает (для ping) и пишет.
  - Таймауты записи, буфер канала, отключение медленного клиента.
  - Проверь `wscat` или маленьким Go-клиентом.
- **Закрепление (30 мин):** [coder/websocket examples](https://github.com/coder/websocket);
  сравни с `gorilla/websocket`, пойми разницу API.
- **Проект (30 мин):** статусы job'а стримятся в WS; финальное сообщение с результатом.
- **Заметки:** почему нельзя писать в соединение из нескольких горутин.

## День 5 — Масштабирование и SSE

- **Теория (40 мин):** несколько инстансов API: in-process hub не работает между ними;
  Redis pub/sub как шина; sticky sessions не решают всё; когда достаточно SSE
  (`text/event-stream`), а когда нужен WebSocket.
- **Практика (90 мин):**
  - Redis pub/sub: воркер публикует событие, каждый API-инстанс подписан и
    раздаёт своим WS-клиентам.
  - Сравни сложность с in-process hub.
  - Сделай SSE-эндпоинт как альтернативу и сравни с WS по коду.
  - Запусти два инстанса API локально (разные порты) и проверь broadcast.
- **Закрепление (30 мин):** `go doc net/http.Flusher`; Redis docs — Pub/Sub.
- **Проект (30 мин):** выбери механизм, обоснуй в README (1 абзац + схема).
- **Заметки:** какие гарантии доставки у pub/sub (никаких) и что с этим делать.

## Типичные ошибки недели

- `go func()` вместо очереди для работы, которую нельзя терять.
- Публикация в очередь до коммита в БД (или наоборот без outbox).
- Обработчик не идемпотентен → дубли при ретраях.
- Запись в WebSocket из нескольких горутин.
- Нет ping/pong и таймаутов → «мёртвые» соединения.
- Hub без блокировки или с блокировкой на время записи.
- Бесконечные ретраи без ограничения и архива.
- Redis как единственное хранилище состояния задачи.

## Гейт недели

```bash
docker compose up -d --build
curl -s -X POST localhost:8080/jobs -H "Idempotency-Key: abc" -d '{"type":"report"}'
curl -s localhost:8080/jobs/<id>
# подключиться к ws://localhost:8080/jobs/<id>/events и увидеть прогресс

# убить воркер посреди задачи
docker compose kill worker
docker compose up -d worker
# задача должна завершиться, статус done
```

- [ ] Сквозной сценарий работает.
- [ ] Падение воркера не теряет задачу.
- [ ] Повторный POST с тем же ключом не создаёт дубль.
